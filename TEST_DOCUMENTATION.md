## 6. Модуль складского учёта: тест-план

Индивидуальное задание практики: консольный модуль учёта товарно-материальных ценностей на складе (приход, списание, контроль остатков, уведомление о минимальном остатке). Подробности — в [разделе 5 отчёта](PRACTICE_REPORT.md#5-индивидуальное-задание).

| Раздел тест-плана | Содержание |
|---|---|
| Объект тестирования | Метод `issue` класса `Product` (списание товара со склада) |
| Цель | Убедиться, что списание работает правильно на допустимых и недопустимых данных |
| Средства | Node.js, консольный интерфейс приложения |
| Методика | Для каждого кейса запустить приложение, ввести количество через консоль, сравнить фактический результат с ожидаемым |
| Предусловие | Начальный остаток товара — 17 единиц |
| Критерий успеха | Все кейсы дают ожидаемый результат. При расхождении заводится дефект, модуль возвращается на доработку |

**Бизнес-процесс «Списание товара»** (по нему составлены проверки):

1. Кладовщик выбирает товар и вводит количество — система показывает текущий остаток.
2. Система проверяет ввод → при ошибке `ValidationError`.
3. Система сравнивает количество с остатком → при нехватке `InsufficientStockError`.
4. Списание и пересчёт остатка в транзакции.
5. Запись операции в журнал.
6. Проверка минимального остатка → при необходимости уведомление о пополнении.

**Правило статуса запаса:** остаток 0 → «Отсутствует»; от 1 до минимального остатка → «Требуется заказ»; выше минимального → «В наличии».

## 7. Классы эквивалентности и граничные значения

Входные данные: количество к списанию `quantity` при остатке 17.

| Класс | Диапазон | Тип | Представитель |
|---|---|---|---|
| Допустимое количество | целое, 1 ≤ q ≤ 17 | допустимый | 5 |
| Ноль | q = 0 | недопустимый | 0 |
| Отрицательное | q < 0 | недопустимый | −5 |
| Больше остатка | q > 17 | недопустимый | 18 |
| Нецелое | дробное число | недопустимый | 2,5 |

Граничные значения: **0 / 1** (нижняя граница) и **17 / 18** (остаток).

## 9. SQL-запросы для проверки данных склада

Схема БД: `product` (товары), `app_user` (пользователи с ролями), `operation` (операции прихода `in` и расхода `out`). Связи «один ко многим»: товар → операции, пользователь → операции. Полная схема — [листинг А.4 отчёта](PRACTICE_REPORT.md#приложение-a), ER-диаграмма — [приложение В](PRACTICE_REPORT.md#приложение-в).

**Журнал операций (JOIN):** кто, что и когда приходовал или списывал.

```sql
SELECT o.id, p.name AS product_name, u.name AS user_name,
       o.type, o.amount, o.datetime
FROM operation o
JOIN product p  ON o.id_product = p.id
JOIN app_user u ON o.id_user = u.id
ORDER BY o.datetime DESC;
```

**Сколько списано по каждому товару (GROUP BY):**

```sql
SELECT p.name, SUM(o.amount) AS total_out
FROM operation o
JOIN product p ON o.id_product = p.id
WHERE o.type = 'out'
GROUP BY p.name
ORDER BY total_out DESC;
```

**Товары с поступлением больше 100 единиц (HAVING):**

```sql
SELECT p.name, SUM(o.amount) AS total_in
FROM operation o
JOIN product p ON o.id_product = p.id
WHERE o.type = 'in'
GROUP BY p.name
HAVING SUM(o.amount) > 100;
```

**Товары без единой операции (LEFT JOIN):**

```sql
SELECT p.id, p.name
FROM product p
LEFT JOIN operation o ON p.id = o.id_product
WHERE o.id IS NULL;
```

**Как запросы помогают при тестировании:**

- после TC-01 журнал (JOIN) должен содержать новую операцию `out` на 5 единиц от нужного пользователя;
- после TC-03 и TC-04 новых записей в журнале быть не должно — неуспешная операция не сохраняется;
- ограничение `CHECK (amount > 0)` в таблице `operation` дополнительно защищает от нулевых и отрицательных операций на уровне БД.

## 10. Оценка качества по ISO/IEC 25010

| Характеристика | Вес | Оценка | Обоснование |
|---|---|---|---|
| Функциональная пригодность | 0,30 | 5 | Есть приход, списание и контроль остатков |
| Надёжность | 0,25 | 5 | Проверка входных данных и обработка исключений |
| Удобство использования | 0,20 | 4 | Консольный интерфейс |
| Сопровождаемость | 0,15 | 5 | Код структурирован, его легко расширять |
| Безопасность | 0,10 | 2 | Нет аутентификации и авторизации |

Интегральная оценка: **Q = 0,30×5 + 0,25×5 + 0,20×4 + 0,15×5 + 0,10×2 = 4,5 из 5**. Слабое место — безопасность, это первый кандидат на доработку.

Требования к надёжности (ГОСТ 34.602–2020) и KPI складского процесса (доля отгрузок, выполненных в срок) — в [разделах 5.6–5.7 отчёта](PRACTICE_REPORT.md#56-разработка-проектной-документации).
